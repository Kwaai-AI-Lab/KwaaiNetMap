# Map v2 — native KwaaiNet

This branch holds the **second-generation** KwaaiNet map: the same three views
as v1, served from a Rust API that reads the DHT through a native `kwaainet`
node instead of the Python petals/hivemind stack.

| | v1 (`main`) | v2 (this branch) |
|---|---|---|
| Data source | Python Hivemind, which forks the standalone Go `p2pd` | rust-libp2p in-process, via `kwaai-p2p` |
| API | Flask on a `health.petals.dev` fork, port 8000 | Rust/Axum, port 3030 |
| v1 endpoints | `/api/v1/state`, `/api/v1/is_reachable/<id>`, `/metrics` | all three, same shapes |
| v2 endpoints | — | `/api/stats`, `/api/nodes`, `WS /api/live`, `/health` |
| UI | `kwaainet.html` — Leaflet map, table, vis.js topology | the same file, served by nginx |
| Deployed | map.kwaai.ai | kwaaimap2, by KwaaiNetOps — no DNS yet |

## Why the v1 API shape is reproduced exactly

`/api/v1/state` is not an internal detail. Every running node's health monitor
polls it (`health_monitoring.api_endpoint` defaults to
`https://map.kwaai.ai/api/v1/state`), and `kwaai-cli`'s `map.rs` reads
`model_reports[].short_name` and `.server_rows` to choose which local model to
serve. A DNS cutover moves that traffic here, so anything this server does not
answer identically breaks a deployed fleet rather than a test.

The page is the same evidence from the other side: it reads
`peer_ip_info.location`, `peer_ip_info.multiaddrs` and `span.server_info`. It
is served unchanged from `docker/kwaainet_health/kwaainet.html` — the parity is
real, not reimplemented.

`map-server/src/snapshot.rs` is where that contract lives.

## What the crawler does

`map-server` runs its own rust-libp2p swarm, in process, through `kwaai-p2p`.
The crawler dials the bootstraps and issues `DHTProtocol.rpc_find` via
`NetworkHandle::call_unary_handler`. One process, no control socket.

**It does not use `kwaai-p2p-daemon`.** That crate wraps the standalone **Go**
libp2p daemon, which KwaaiNet has replaced with rust-libp2p; its build script
also needs a Go toolchain to compile the Go binary, which is why it is absent
from `Dockerfile.map-server`. An earlier draft of this server drove a separate
`kwaainet` process over that daemon's control protocol — that whole layer is
gone.

The swarm is an **observer**, and structurally so rather than by configuration:
it never calls the announce path, and `dht_server: false` keeps Kademlia a
client that answers nobody else's queries. There is no `announce_self` flag
involved, which matters — that key does not exist before kwaainet v0.6.3, and
config is parsed without `deny_unknown_fields`, so an older binary accepts it,
ignores it, and announces itself as a serving node offering blocks it does not
have. Nothing here can regress that way, because there is no flag to ignore.

One pass:

1. Dial every bootstrap. Reachability is `bootstrap_states`; the connections
   are then reused for the queries below.
2. Read `_petals.models` for the models on the network and their block counts.
3. For each model, query every block key in one batched `FindRequest`. Results
   are positionally aligned with the keys sent, which is how a record is mapped
   back to a block index — and why the model dimension survives into
   `model_reports` rather than being flattened to a peer set.
4. Read `_kwaai.vpk.nodes` and `_kwaai.inference.nodes`, so a node announcing a
   capability but no blocks is still counted.
5. `list_peers` for addresses, then geolocate. DHT records carry peer ids, never
   addresses, so a peer the observer holds no connection to has no location —
   the same limit v1 had. `list_peers` reports one entry per connection, so the
   addresses are grouped back per peer.

## Building the server

Two `kwaai-*` dependencies from crates.io — `kwaai-p2p` and
`kwaai-hivemind-dht` — rather than the KwaaiNet workspace. Bump them together.

```bash
cd map-server
bash patches/fetch-multistream-select.sh   # required once, before any cargo command
cargo build --release && cargo test
```

The build needs **protoc** for the DHT protos and nothing else. No Go: that
requirement belonged to `kwaai-p2p-daemon`, which this no longer depends on.

### The multistream-select patch

The hivemind DHT negotiates **bare handler names** — `DHTProtocol.rpc_find` —
as libp2p protocol IDs. go-libp2p accepts them; rust-libp2p's
multistream-select rejects any name without a leading `/`. `patches/` carries
the same one-file relaxation KwaaiNet keeps in `core/patches/`, applied through
`[patch.crates-io]`.

It has to be repeated here rather than inherited: `[patch.crates-io]` applies
only to the root manifest of a build, and this crate builds standalone rather
than inside the KwaaiNet workspace.

Without it **the crawler cannot read the DHT at all** — every `rpc_find` is
refused dialer-side with `Transport error: A protocol (name) is invalid`. The
failure mode is the dangerous kind: an empty crawl looks exactly like an empty
network, so the map serves a plausible, well-formed, entirely wrong document.
Testing against an unreachable bootstrap cannot tell the two apart; testing
against a real DHT can, which is what the kwaaiai-env NAT bed is for.

## Running it

| env | meaning |
|---|---|
| `BOOTSTRAP_PEERS` | space-separated multiaddrs, each **including `/p2p/<PeerId>`** |
| `BIND_ADDR` | listen address, default `0.0.0.0:3030` |
| `TOTAL_BLOCKS` | blocks to measure coverage against; **unset means the largest model the DHT registers**, which is right more often than a fixed number |
| `GEOIP_ENABLED` | `0` disables ip-api.com lookups; every node then sits at the page's fallback pin |
| `GEOIP_STATIC_FILE` | path to a JSON file of pins by IP, see below; those IPs are placed as written, lookups on or off, reserved ranges included |
| `ALLOWED_ORIGINS` | CORS, default `*` |

`BOOTSTRAP_PEERS` is required: the server refuses to start without it rather
than crawling an empty network.

The crawler skips any bootstrap entry without a `/p2p/` component, so a bare
`/ip4/.../tcp/8000` leaves it with nothing to ask.

Locally:

```bash
BOOTSTRAP_PEERS="/ip4/…/tcp/8000/p2p/12D3KooW…" \
  docker compose -f docker-compose.map.yml up
```

### Static locations

`GEOIP_STATIC_FILE` is for networks on address space ip-api.com cannot place
— a sealed test bed on 198.18/15, a ULA, a lab LAN. It names a JSON object
keyed by IP, v4 or v6 as it appears in the multiaddr (no brackets, no
prefix length), each value a location:

```json
{
  "198.18.0.20":   { "country": "United States", "city": "Los Angeles", "lat": 34.0522, "lon": -118.2437, "isp": "NAT-test" },
  "fdc6:1200::20": { "country": "United States", "city": "Los Angeles", "lat": 34.0522, "lon": -118.2437, "isp": "NAT-test" }
}
```

Every field is optional and defaults to empty or zero; `lat`/`lon` are
decimal degrees. Entries are consulted before the public-IP filter and before
any lookup, so a listed IP is pinned whether `GEOIP_ENABLED` is on or off and
whatever range it is in. A peer whose own address is listed gets that pin; a
relayed peer whose relay is listed borrows the relay's pin as "Via relay",
exactly as a looked-up relay would. An unreadable or malformed file logs a
warning and the map runs without pins rather than refusing to start.

## Deployment

Images are built and pushed to GHCR by `.github/workflows/build-images.yml`.
Nothing here deploys: **KwaaiNetOps** owns which host runs which tag
(`terraform/kwaaimap2.tf`, `var.map_image_tag`), so no workflow in this repo can
change what production serves.

`kwaaimap2` runs alongside `kwaaimap1`. The v1 map keeps serving
`map.kwaai.ai` until someone moves the Cloudflare record by hand.

## The React SPA (removed)

A React landing page — hero stats, benchmark, trust graph, install funnel —
written in March 2026 and never finished. Removed rather than parked: it is
not what deploys, and parked code mostly confuses the next reader about what
is live. The full source survives at the **`archive/map-spa`** branch if the
benchmark worker or trust-graph components ever want harvesting.
`MAP_SERVER_V2_REQUIREMENTS.md` remains the design of record for folding
those features into the map proper.

## Layout

```
map-server/           Rust API and DHT crawler
  src/observer.rs     the in-process rust-libp2p swarm
  src/snapshot.rs     the /api/v1/state wire types — the published contract
  src/crawler.rs      one crawl pass, per model
  src/dht.rs          Hivemind Ext(64)/Ext(80) record decoders
  src/geoip.rs        address to map pin
  src/reachability.rs /api/v1/is_reachable probes
docker/map-nginx.conf      serves the page, proxies /api/ /metrics /health
Dockerfile.map-server      the API image — one binary, no node beside it
Dockerfile.map-frontend    the page image
docker-compose.map.yml     the deployed stack, for local runs
```
